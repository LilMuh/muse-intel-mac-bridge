# 微信待处理消息缓存 · 设计

日期：2026-09-28
分支：`feat/wechat-read-image`（接在读图功能后面）

## 目标

不丢消息。`wechat-unread` 读到的新消息先放进 Mac 本地的「待处理缓存」，一直留到 Muse 处理完为止：回复成功时自动清掉，不需要回复的由 Muse 手动确认清掉。Muse 随时可以查看完整的待处理列表，不用碰微信。

## 现在为什么会丢消息

1. **交付即消耗**：`--unread` 一返回消息，读取进度（`~/.cache/wx-send/cursor/`）就往前推了，下次只返回更新的消息。Muse 这一轮如果没处理完（上下文丢了、出错、忘了回），这些消息不会再出现。
2. **先推进进度、后输出结果**：`readNew` 每读完一个聊天就立刻保存读取进度，而结果要等所有聊天都读完才一起输出。中途退出（比如退出码 6：微信被切走）时，已读聊天的进度推进了，结果却没输出，这些消息就永久丢了。
3. **标回未读只剩一个标记**：显示「1条未读」，原来有几条、是哪几条都不知道了。

## 已确定的决定

- 清除规则：回复成功就清掉这个聊天的待处理消息；不需要回复的用 `wechat-ack` 手动清。
- 更新时机：只在 Muse 调用 `wechat-unread` 时去微信读新消息、写进缓存；不做后台定时读取。
- 读完未读后固定切到「文件传输助手」（已实现，提交 `b7943ad`）。

## 不做的事

- 后台定时读取、监听微信
- `wechat-read` 读到的消息进缓存（它是主动查看某个聊天，不代表未读）
- 待处理消息自动过期（不自动删除，只能靠回复或确认清掉）

## 设计

### 1. 存储（Python 服务端负责）

`~/.cache/wx-send/pending/<账号>.json`。没有指定账号时，账号名用 `default`。

```json
{"next_id": 43,
 "chats": {"张三": {"group": false, "messages": [
     {"id": 41, "text": "明天几点？", "time": "15:42", "added": "2026-09-28T15:43:10"},
     {"id": 42, "text": "图片", "image": "in-20260928-154310-1.png", "time": "15:42", "added": "2026-09-28T15:43:10"}]}}}
```

- 只存 `type == "message"` 的消息。时间行不单独存，把它前面最近的一个时间写进后面每条消息的 `time`。群聊消息保留 `from` / `sender` / `wxid`，图片保留 `image`。
- `id` 按账号递增。
- 写文件时先写临时文件再改名（原子替换），避免写到一半程序退出、把缓存写坏。
- 服务端对所有 POST 请求都加了全局锁，所以同一时间只有一个请求在读写缓存。

### 2. 接口

| 接口 | 行为 |
|---|---|
| `POST /wechat/unread` | 照常去微信读新消息，把新消息放进缓存并编号。返回里新增 `pending`：`{"聊天名": {"group": …, "messages": [...]}}`，是**所有还没处理的消息**，其中这次新读到的标 `"new": true`。原来的 `chats` 字段保留。`list_only` 时不读微信，只附带 `pending`。 |
| `POST /wechat/pending {"account?"}` | 只读缓存，不碰微信，立刻返回 `{"ok", "pending": {…}, "count": N}`。 |
| `POST /wechat/ack {"chat", "account?", "upto_id?"}` | 清掉这个聊天的待处理消息；给了 `upto_id` 就只清 `id ≤ upto_id` 的。返回清掉了几条。聊天名在缓存里不存在时返回 400。 |
| `POST /wechat/send` | 发送前记下这个聊天当前最大的待处理 `id`。只有真的发送成功（`status == "ok"`，而且不是 `dry_run`），才清掉 `id ≤` 这个值的消息。返回里新增 `"acked": 清掉的条数`。`unconfirmed_do_not_retry` 或其他失败都不清。 |

聊天名按缓存里的名字精确匹配。缓存里的聊天名来自 `--unread` 返回的名字，发送时用的也是这个名字。

### 3. 不丢消息的保证（Swift 改一处）

- **读取进度改为最后才保存**：`readNew` 不再立刻 `saveCursor`，而是把要保存的进度记在列表里；`printUnreadDetails` 成功输出 JSON 之后，再统一保存。中途抛错退出的话，一条进度都不保存，下次会把这些消息重新读出来。
- **服务端先写缓存再返回**：解析 wx-send 的输出后，先把新消息写进缓存，再回复 HTTP 请求。如果缓存写失败，请求返回错误，并在错误信息里带上原始输出，不会悄悄丢掉。
- **重复**：进度只在成功输出后才保存，而成功输出就一定会写进缓存，所以同一批消息不会进两次缓存。唯一的例外是 Swift 已经输出、服务端还没写完缓存时服务端崩溃，这种情况下次会重读，可能多出一份，这是可以接受的。
- **读取进度找不到上次的位置**（note「没找到上次读到的位置」）：这批消息照样进缓存，并在每条上标 `"note"`，提醒 Muse 可能和以前的消息有重复或有遗漏。

### 3.1 读了谁就要未读谁

点开一个聊天，它在微信里就变成已读了。读取中途出错、被切走或者程序被杀掉，没来得及标回未读的聊天，下次读未读就找不到了，只推迟保存读取进度救不回来。所以：

1. **点开之前先记账**：点开前把「聊天名 → 当时的未读条数」写进 `~/.cache/wx-send/remark-<账号>.json`，成功标回未读后才删掉这一条。
2. **每次读未读，先补标**：先切到「文件传输助手」，再把账上还没标回的聊天逐个标回未读，然后才扫描未读列表。
3. **未读条数取较大值**：标回未读后，微信只显示「1条未读」。所以读的时候，未读条数取「列表上显示的」和「账上记的」两者中较大的那个。
4. **标回未读更可靠**：失败时再重试 2 次；判断是否成功时，`N条未读` 和免打扰群的 `[N条]` 都认。
5. **出错时也要标回**：只要微信还在最前面，出错退出前就把点开过的聊天标回去；如果是被用户切走了，就不去抢焦点，留到下次调用时补标。
6. 这次读过的每个聊天（包括读的时候出错的）都会标回未读，`remarked_unread` 如实报告结果。「文件传输助手」自己被读到时是例外：读完会停在它上面，所以不标回，直接从账上删掉。

### 4. 图片

- `inbox/` 的自动清理从 bash 挪到服务端：带 `images` 读消息之前，删掉超过 `WX_INBOX_DAYS` 天的 `in-*` 文件，但**跳过缓存里还在引用的文件**。wx-send.sh 里原来的清理代码删掉。
- 待处理消息被清掉以后，它引用的图片按天数正常清理。

### 5. mab.py

- 新增 `wechat-pending [-a]`、`wechat-ack 聊天名 [--upto ID] [-a]`。
- `wechat-unread --images`：`pending` 里带 `image` 的消息也要下载，下载时按文件名去重，同一张图只下载一次。
- `wechat-send` 的输出里多了 `acked`，不需要额外处理。

### 6. muse-prompt 的工作流程

1. 调用 `wechat-unread`（需要看图时加 `--images`）。
2. 以返回的 `pending` 为准逐个处理聊天，不能只看 `new` 的消息：
   - 需要回复的就回复。回复成功会自动清掉这个聊天在回复前的待处理消息。
   - 不需要回复的，调用 `wechat-ack 聊天名`。
3. 任何时候想知道还有什么没处理，调用 `wechat-pending`，它不碰微信，马上返回。

## 边界情况

| 情况 | 处理 |
|---|---|
| 读到一半中断（退出码 5 或 6，超时） | 不输出、不保存进度、不写缓存，下次重读 |
| Muse 回复时，这个聊天又来了新消息 | 新消息只有在下一次 `unread` 时才会进缓存，而这次回复只清发送前已有的 id，所以新消息不会被误清 |
| 回复群聊 | 同样清掉这个群在发送前的全部待处理消息（在群里回复一次，就算把这个群处理完了） |
| 回复一个不在缓存里的聊天 | 照常发送，`acked: 0` |
| 试运行发送 | 不清 |
| 两个账号 | 各自一个缓存文件，互不影响 |

## 测试

- **Python 单元测试**：
  - 缓存的读写：编号递增、原子替换、时间归并到消息上、群聊字段保留
  - `/wechat/unread`：新消息进缓存并标 `new`；上次没处理的消息仍在 `pending` 里；`wx-send` 失败时缓存不变
  - `/wechat/pending`、`/wechat/ack`（全部清、`upto_id`、聊天名不存在时 400）
  - `/wechat/send`：成功时清、失败或 `unconfirmed` 或试运行时不清；只清发送前已有的 id
  - inbox 清理跳过缓存里引用的图片
  - mab 的 `wechat-pending`、`wechat-ack`，以及 pending 里图片的下载和去重
- **Swift**：延后保存读取进度。用类型检查验证；再做一次真机验证：读未读时在读第二个聊天的过程中把微信切走，确认第一个聊天的进度没有推进，下次还能读出来。
- **真机**（zhiwuzhu ↔ work，限制只读 1 个聊天时直接给 wx-send 设 `WX_UNREAD_MAX_CHATS`，或者给 mab 传 `--max-chats 1`）：
  - work 发消息 → `unread` 进缓存 → 不回复 → 再次 `unread`，旧消息仍在 `pending` 里
  - zhiwuzhu 回复 → 缓存清空
  - 另一条消息用 `ack` 清掉
